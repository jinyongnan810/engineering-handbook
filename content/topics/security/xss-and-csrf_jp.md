# XSSとCSRFガイド

## 1. 全体像

**XSS** と **CSRF** はどちらもWebセキュリティ上の重大な問題ですが、攻撃対象となる「信頼関係」が異なります。

| 攻撃手法 | 攻撃者が悪用するもの                                   | 主な被害者                      |
| -------- | ------------------------------------------------------ | ------------------------------- |
| **XSS**  | ブラウザがWebサイトに対して持つ信頼                    | Webサイトの閲覧ユーザー         |
| **CSRF** | サーバーがログイン中ユーザーのブラウザに対して持つ信頼 | サーバー / ユーザーのアカウント |

大まかにまとめると:

```text
XSS  = 攻撃者がサイト上で悪意のあるJavaScriptを実行させる
CSRF = 攻撃者が被害者のブラウザに意図しないリクエストを送信させる
```

---

# 2. XSS: クロスサイトスクリプティング (Cross-Site Scripting)

## XSSとは何か

**XSSは、信頼できないデータがWebページに挿入され、ブラウザがそれを実行可能なコードとして処理してしまうことで発生します。**

例: ユーザーのコメントを表示するコメントシステム。

通常のコメント:

```text
素晴らしい記事ですね！
```

悪意のあるコメント:

```html
<script>
  alert("hacked");
</script>
```

WebサイトがこれをそのままHTMLに出力すると、ブラウザがスクリプトを実行してしまいます。

---

## XSSで何ができるのか？

サイトの実装状況に応じて、XSSは以下のような悪用が可能です:

- ページ上に表示されているデータの窃取
- ログイン中ユーザーとしての操作代行
- `localStorage` に保存されているトークンの読み取り
- ページコンテンツの改ざん
- 偽のログインページへのリダイレクト（フィッシング）
- ユーザーのセッションを利用したリクエストの送信

危険な例:

```js
fetch("/api/account/delete", { method: "POST" });
```

攻撃者のスクリプトがサイト内で実行されると、そのユーザーの権限でAPIを呼び出すことができてしまいます。

---

# 3. XSSの種類

## 3.1 格納型XSS (Stored XSS)

悪意のあるスクリプトがサーバーのデータベース等に恒久的に保存されます。

例:

```text
攻撃者が悪質なコメントを投稿
↓
サーバーがそれを保存
↓
他のユーザーがそのページを開く
↓
被害者のブラウザでスクリプトが実行される
```

多くのユーザーに影響が及ぶため、極めて危険です。

---

## 3.2 反射型XSS (Reflected XSS)

悪意のある入力が現在のリクエスト（多くはURLパラメータ）から直接反射されます。

URLの例:

```text
https://example.com/search?q=<script>alert("XSS")</script>
```

脆弱なページ:

```html
<p>
  Search results for:
  <script>
    alert("XSS");
  </script>
</p>
```

通常、被害者に細工されたリンクをクリックさせる必要があります。

---

## 3.3 DOM-based XSS

サーバー側は安全であっても、クライアント側のJavaScriptがページ内に危険なコンテンツを挿入してしまうことで発生します。

脆弱なコード例:

```js
const name = new URLSearchParams(location.search).get("name");
document.body.innerHTML = "Hello " + name;
```

URL:

```text
https://example.com/?name=<img src=x onerror=alert(1)>
```

原因は `innerHTML` の使用です。

より安全な実装:

```js
const name = new URLSearchParams(location.search).get("name");
document.body.textContent = "Hello " + name;
```

`textContent` は入力をHTMLではなく単なるテキストとして扱います。

---

# 4. XSSの防御策

## サーバー側の防御

### 1. 出力のエスケープ (Escape output)

最も重要な鉄則:

```text
HTMLにデータを挿入する際は、必ずデータをエスケープする。
```

例えば、以下のコード:

```html
<script>
  alert("XSS");
</script>
```

は次のようにエスケープされるべきです:

```html
&lt;script&gt;alert("XSS")&lt;/script&gt;
```

これにより、ブラウザはコードを実行せず、単なる文字列として表示します。

---

### 2. 許可されたHTMLのサニタイズ (Sanitize allowed HTML)

場合によっては、以下のように限定的なHTMLタグを意図的に許可したいことがあります:

```html
<b>Hello</b> <a href="...">link</a>
```

この場合、すべてをエスケープしてしまうと意図通りの表示ができません。

そのため、HTMLサニタイザー（HTML Sanitizer）ライブラリを使用します。

サニタイザーは以下のような危険な要素を取り除きます:

```html
<script>
onerror=
onclick=
javascript:
```

危険な入力の例:

```html
<img src="x" onerror="alert(1)" />
```

サニタイズ後の安全な出力:

```html
<img src="x" />
```

---

### 3. コンテンツセキュリティポリシー (CSP) の利用

CSPはサーバーから送信されるブラウザのセキュリティポリシーヘッダーです。

例:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

これにより、スクリプトの読み込み元が制限されます。

堅牢なCSPを設定することで、多くのXSSペイロード（特にインラインスクリプト）の実行をブロックできます。

ただし、CSPはエスケープ処理の**代替ではありません**。多層防御の第2のレイヤーとして機能します。

---

### 4. 安全なCookie設定の使用

セッションCookieの設定例:

```http
Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Lax
```

重要な属性:

| 属性       | 目的                                 |
| ---------- | ------------------------------------ |
| `HttpOnly` | JavaScriptからのCookie読み取りを禁止 |
| `Secure`   | HTTPS通信時のみCookieを送信          |
| `SameSite` | CSRFリスクを低減                     |

`HttpOnly` はXSSによるCookie盗難を防ぐのに役立ちます。

ただし注意点として、`HttpOnly` が設定されていても、感染したページからユーザーのセッションを使ってリクエストを送信することは可能です。

したがって、`HttpOnly` は被害を軽減するものであり、XSSそのものを完全に防ぐわけではありません。

---

## クライアント側の防御

### 1. 信頼できないデータに対する `innerHTML` の使用を避ける

危険:

```js
element.innerHTML = userInput;
```

安全:

```js
element.textContent = userInput;
```

Reactにおける安全なデフォルト動作:

```tsx
<div>{userInput}</div>
```

Reactはデフォルトで文字列をエスケープします。

Reactにおける危険なコード:

```tsx
<div dangerouslySetInnerHTML={{ __html: userInput }} />
```

これはサニタイズされた安全なHTMLに対してのみ使用してください。

---

### 2. 機密トークンを `localStorage` に保存しない

XSSが発生した場合、JavaScriptから簡単に読み取られてしまいます:

```js
localStorage.getItem("access_token");
```

そのため、認証トークンを `localStorage` に保存するとXSS時の影響が拡大します。

多くの従来のWebアプリケーションにおける安全なパターン:

```text
セッションCookie + HttpOnly + Secure + SameSite
```

---

# 5. XSS防御の限界

単一の防御策だけで十分なものはありません。

| 防御策             | 限界・注意点                                              |
| ------------------ | --------------------------------------------------------- |
| エスケープ         | HTML、属性、JS、URLなど文脈に応じた適切なエスケープが必要 |
| サニタイズ         | 自前実装は極めて難しく、実績あるライブラリが必要          |
| CSP                | 設定ミスやバイパス手法が存在する可能性がある              |
| HttpOnly Cookie    | Cookieの盗難は防げるが、XSSによる操作代行は防げない       |
| Reactのエスケープ  | `dangerouslySetInnerHTML` には効果がない                  |
| 入力バリデーション | これ単体では不十分。出力時のエスケープが不可欠            |

---

# 6. CSRF: クロスサイトリクエストフォージェリ (Cross-Site Request Forgery)

## CSRFとは何か

**CSRFは、攻撃者がログイン中のユーザーのブラウザを騙し、別のWebサイトに対して意図しないリクエストを送信させる攻撃です。**

重要なポイント:

```text
ブラウザは対象サイト向けのCookieを自動的にリクエストに付与して送信する。
```

ユーザーが以下のサイトにログイン中だとします:

```text
https://bank.example.com
```

ユーザーのブラウザはそのサイトのセッションCookieを保持しています。

その状態で、ユーザーが攻撃者の作成した悪意あるページを閲覧します:

```text
https://evil.example.com
```

攻撃者のページは、銀行サイトに対して不正なリクエストを送信させようとします。

---

## シンプルなCSRFの例

脆弱な銀行のエンドポイントを想定します:

```http
POST /transfer
```

リクエストボディ:

```text
to=attacker&amount=1000
```

攻撃者は以下のようなページを作成します:

```html
<form action="https://bank.example.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="1000" />
</form>

<script>
  document.forms[0].submit();
</script>
```

被害者が銀行にログイン中であれば、ブラウザは自動的に銀行のセッションCookieを添付して送信します。

銀行側から見ると:

```text
被害者のブラウザから送信された正当なリクエストに見えてしまう。
```

これがCSRFです。

---

# 7. CSRFで何ができるのか？

CSRFは通常、以下のような**状態を変更する操作（State-changing actions）**を実行させます:

- メールアドレスの変更
- パスワードの変更（旧パスワードの入力が不要な場合）
- フォームの送信
- 送金処理
- データの削除
- 「いいね！」、フォロー、投稿などの操作
- アカウント設定の変更

ブラウザの同一生成元ポリシー（Same-Origin Policy）により、攻撃者は通常レスポンスの内容を直接読み取ることはできません。

したがって、CSRFの本質は次の通りです:

```text
ページ内容を盗むのではなく、不正な操作を強制すること
```

---

# 8. CSRFの防御策

## サーバー側の防御

### 1. CSRFトークン

#### CSRFトークンの主な方式

- **同期トークンパターン (Synchronized token pattern)**: サーバーがランダムなトークンを生成してユーザーセッションに保存し、フォーム内に含めます。サーバーは送信されたトークンがセッションの値と一致するか検証します。
- **Double Submit Cookieパターン**: サーバーがランダムなトークンを含むCookieを発行します。クライアントはその値を読み取り、リクエストヘッダーまたはフォームフィールドに含めて送信します。サーバーはヘッダーの値とCookieの値が一致するか検証します。

#### CSRFトークンが有効な理由

- 同一生成元ポリシーにより、攻撃者のサイトから被害者のページのトークンを盗み出すことはできません。
- 仮にトークンの値を知っていたとしても、通常のHTMLフォーム送信ではカスタムHTTPヘッダーを付与できません。またAPIからトークンを取得しようとしても、CORSポリシーによってブロックされます。
  - メモ: 通常のフォーム送信はCORSの制限を受けずに送信できます。

---

### 2. SameSite Cookie

Cookieに `SameSite` 属性を設定します。

例:

```http
Set-Cookie: session=abc; SameSite=Lax; Secure; HttpOnly
```

主な値:

| 設定値   | 動作                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| `Strict` | クロスサイトのリクエストには一切Cookieを送信しない                                                                 |
| `Lax`    | 通常のトップレベル遷移（外部リンクのクリックなど）では送信されるが、多くのクロスサイトPOSTリクエストでは制限される |
| `None`   | クロスサイトでもCookieを送信（`Secure` 属性が必須）                                                                |

---

### 3. Origin / Referer ヘッダーの検証

機密性の高いリクエストに対して、サーバー側でヘッダーを検証します:

```http
Origin: https://app.example.com
```

送信元オリジンが信頼できない場合はリクエストを拒否します。

多層防御の追加層として有用ですが、環境やプライバシー設定によってはヘッダーが欠落する場合があるため、これ単体を唯一の防御策にすべきではありません。

---

### 4. 重要な操作に対する再認証の要求

極めて重要な操作については、パスワードの再入力を求めます。

例:

```text
パスワードの変更
アカウントの削除
振込先銀行口座の変更
高額の送金
```

これにより、万が一CSRFやXSSが存在しても被害を限定できます。

---

## クライアント側の防御

CSRFは主に**サーバー側の課題**ですが、クライアント側でも以下の対応を行います。

### 1. APIリクエストにCSRFトークンを含める

```js
fetch("/api/profile", {
  method: "POST",
  headers: {
    "X-CSRFToken": csrfToken,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ displayName: "Alice" }),
});
```

サーバー側でこのトークンを検証します。

---

### 2. 同一オリジンのAPI設計を採用する

可能な限り同一オリジンでの構成を優先します:

```text
フロントエンド: https://app.example.com
API:           https://app.example.com/api
```

これにより、CookieやCSRFのハンドリングがシンプルになります。
クロスドメイン構成では、CORS、Cookie、CSRFのより厳密な設定が必要になります。

---

### 3. クロスサイト資格情報（Credentials）を安易に許可しない

危険なCORS設定パターン:

```http
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: *
```

現代のブラウザではこの組み合わせは無効化されますが、考え方として非常に危険です。
資格情報を許可する場合は、信頼できるオリジンのみを明示的に指定します:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

---

# 9. CSRF防御の限界

| 防御策                | 限界・注意点                                                               |
| --------------------- | -------------------------------------------------------------------------- |
| CSRFトークン          | ページ内にXSSが存在する場合、トークンが読み取られてバイパスされる          |
| SameSite Cookie       | 同一ドメイン配下のサブサイトが侵害された場合、Cookieが送信される恐れがある |
| GETではなくPOSTを使用 | 基本的なマナーだが、単体ではCSRFを防げない                                 |
| Origin/Referer検証    | ヘッダーが欠落している場合がある                                           |
| 再認証                | セキュリティとUXのトレードオフを考慮する必要がある                         |

極めて重要な原則:

```text
XSSが存在すると、CSRF防御は容易に突破されます。
```

なぜなら、攻撃者のJavaScriptが正規のサイト上で実行できれば、ページ内からCSRFトークンを読み取って有効なリクエストを送信できてしまうためです。

したがって:

```text
CSRF対策を行ってもXSSは防げない。
XSS対策こそが、より根本的な基盤となる。
```

---

# 10. XSSとCSRFの比較まとめ

| 比較項目                           | XSS                           | CSRF                                 |
| ---------------------------------- | ----------------------------- | ------------------------------------ |
| 攻撃者はサイト上でJSを実行するか？ | はい                          | 通常はいいえ                         |
| 被害者のログインが必要か？         | 不要な場合もあるが多い        | 通常は必須                           |
| 攻撃者はページデータを盗めるか？   | 多くの場合可能                | 通常は不可                           |
| 攻撃者は操作を代行できるか？       | 可能                          | 可能                                 |
| 主な防御策                         | エスケープ / サニタイズ / CSP | CSRFトークン / SameSite / Origin検証 |
| 主な対策場所                       | サーバー側 ＆ クライアント側  | 主にサーバー側                       |

# 11. メンタルモデル（思考フレームワーク）

## XSSのメンタルモデル

自問すること:

```text
攻撃者が制御可能な文字列が、HTML・JavaScript・CSS・URLとして解釈される可能性はあるか？
```

該当する場合は警戒が必要です。

対策:

```text
デフォルトでエスケープする。
HTMLを許可する場合はサニタイズする。
innerHTML の使用を避ける。
バックアップとしてCSPを導入する。
```

---

## CSRFのメンタルモデル

自問すること:

```text
外部のWebサイトが、ユーザーのブラウザにCookie付きでこのリクエストを勝手に送信できるか？
```

該当する場合は保護が必要です。

対策:

```text
CSRFトークンを検証する。
SameSite Cookieを使用する。
Originヘッダーを検証する。
状態を変更する操作にGETリクエストを使わない。
重要な操作には再認証を要求する。
```
